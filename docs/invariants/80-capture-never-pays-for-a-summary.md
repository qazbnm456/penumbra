# Invariant 80: Capture never pays for a summary by default

**Capture makes no model call unless the operator turns it on: distillation (`distill.py`) is a separate pass, off by default and bounded by a batch size capped at 500, a failed summary leaves the node at `ready_undistilled` instead of costing the capture, concept alignment runs only at the end of a pass the reader pressed, and organising captures into orbits (the kit's `organize_pending`) only in the automatic filing mode the reader chose.**

## Why this is a product rule

This project is bring-your-own-key: the reader supplies the model credentials, so every call is their money. The interface's whole message is "just throw everything in". Together, distilling at intake would mean importing 200 bookmarks silently spends 200 calls the reader never asked for, from a surface designed to stop them thinking about whether to keep something. The decision is stated here rather than cited, because the working note that settled it is not tracked.

So intake leaves a stored capture at `ready_undistilled` and stops. `distil_pending` is a separate entry point with a `limit` the caller names, never "everything", and `GET /horizon` reports the `undistilled` count, so the cost is known before anything runs. That is invariant 47's "no action starts without an explicit press" applied to money. A reader can capture all week and summarise nothing.

## What a summary pass may spend, and what follows it

The pass is the kit's labelling pass (`distill_pending` in `rlm_harness.memory_tasks`), and Penumbra decides which captures it takes and what their state is. A short capture (up to `SHORT_LIMIT`, 12,000 characters of its stored text) is one call that reads the whole text, the kit's `SummariseShort`. A long one is the kit's `DistillLongItem`, an RLM run in a worker subprocess (invariant 21) that reads the whole text from a section map, which costs several calls. The summarise buttons say so before the press: `GET /horizon/distil/estimate` counts the long captures waiting and the label gives a range rather than a single number.

Concept alignment (the kit's `align_pending` and its `AlignEntities` task, in a worker) is the other model call the pass can make, and it follows the same rule: it runs only at the end of a pass the reader pressed, never on its own and never after the automatic pass, once per pass, over at most 60 names no alignment has seen before (the kit's `unseen_entities`), and not at all while fewer than two names are in use. A stopped pass does not go on to align, and the pass's Stop ends a long-document or alignment worker at once rather than after it finishes. The estimate is a bound rather than a guess: the top of its range counts every long document and the one alignment run at the full budget an RLM run is capped by (its steps, its sub-model calls, the one extraction when the steps run out, times the whole-run retries allowed), and the per-orbit summarise button shows it as a number; the Horizon's own button says in words that long captures and alignment take more. A failed alignment is reported beside the pass and leaves its names unseen, so the next pass tries again; the same names failing twice are set aside, so a persistent failure is not paid for at the end of every pass. A Stop is not reported as a failure.

By default the automatic pass leaves long captures for a press. It runs on the intake worker's thread, and an RLM run holding that thread for minutes would keep a capture dropped meanwhile at `queued`. With long ones deferred, each capture in a batch is one call. `auto_distil_long` (`PN_AUTO_DISTIL_LONG` or the settings page) lets it take them too, for a model fast or local enough that neither the wait nor the extra calls matter. It does not align either, for the same reason; the names it writes are aligned at the end of the next pass the reader presses.

## Organising, in automatic filing only

Automatic filing (`filing_mode` = `auto`) is the one other place a pass spends. The local suggestions file what shares entities and tags with an orbit for free; what they cannot place is either the start of a new subject or a match they cannot see, such as two captures that name one subject differently. So at the end of every summary pass, pressed or automatic, the kit's organising pass (`organize_pending`, its `OrganiseBatch` a `dspy.Predict` run in a worker subprocess) sees up to 40 summarised captures in no orbit and the orbits there are, each a kit topic (`topics.py`), and says where each goes: an orbit that exists, a new orbit it names, or nowhere yet. It is one short call a round, unlike alignment, so the automatic pass makes it too, but only once no capture is still arriving, so a burst of captures is organised once rather than after every batch.

The reply is a proposal, and the kit's `plan_from` keeps what it may do: only captures the call was shown, each once, and orbits that exist; a new name equal to an existing orbit's title is that orbit, and past ten new orbits a call the rest wait. The prompt says to leave a capture rather than put unrelated subjects together to stay under that number, because a cap of five over 40 captures on seven subjects merged AI with space exploration and filed coffee and baking under health. A new orbit needs two captures, because without that rule a full run opened two orbits of one source each, and it keeps only when two were actually filed into it: when filing refuses one of two (the corpus cap), the other is taken back and the orbit made for them goes. A placement into an existing orbit counts only when the model states that the capture is about the orbit's subject or a part of it; a loose fit leaves it, because asking for “the closest orbit” filed a lighthouse under astronomy and origami under Taiwanese history. Such a capture waits and is sent again beside the next new captures, so it gets its orbit when a second capture on its subject arrives. A round that filed something is followed by another over what it left, at most three rounds a pass.

Penumbra has the say in every placement (`api._OrganizeHost`, through the kit's `on_place`): each filing goes through `api._file_status` like any automatic one, so the corpus cap holds, a capture already in an orbit is not moved, and a pair the reader declined or took a capture out of is never filed (the kit also refuses it, since the reader's removal is a `said` row). A new orbit is made just before its first capture goes in, and whatever the pass takes back is undone there too, with every orbit the pass made and left empty removed at the end. A filing is announced only once the pass is over and only if it stayed. Captures the model left alone, and captures it placed where filing then refused, are not sent again on their own; they go again when the set of orbits changes or beside new captures. Which ones were left, and against which orbits, is kept in the kit's memory store (`left_items`), since process state was gone after a restart and the waiting card could no longer say why they wait; a Stop leaves what the pass had not reached undecided. It never runs in the manual or assign modes, after a stopped pass or while the model is not answering; it has its own line in the status and on the failure card, and the pass's Stop ends it.

The reader who wants none of this keeps the default, manual, where nothing is filed or created behind them. That is why it is a mode the reader chooses rather than something automatic summarising turns on.

## The toggle and its bound

`auto_distil` (`config.auto_distil_enabled`) is a settings-page option, and `test_the_settings_page_renders_every_setting_the_server_stores` fails if the server stores a setting the page does not draw, because a key without a row is erased by the next Save. It is allowed there although invariant 41 keeps safety bounds off that page, because `POST /horizon/distil` already lets any token holder cause model calls. The toggle changes when spending happens, not whether a token holder can cause it, so it adds no new exposure. Each pass, automatic or pressed, takes at most the batch size (`config.distil_batch_size`: `PN_DISTIL_BATCH` or the settings page, 20 by default, never more than 500, the most `POST /horizon/distil` accepts), so a flipped toggle spends at most one batch per idle.

The automatic path lives in `api.py`, not `intake.py`. The queue exposes an idle hook and imports nothing model-related, so the default is structural: capture cannot be made to spend money by editing the queue. The automatic pass shares the manual pass's progress state, so it is visible, stoppable and cannot overlap a manual pass (invariant 47).

## A capture the pass keeps failing on is set aside

The queue is one query, `horizon.waiting_ids`, which every pass takes from and every count reports: captures that are memory items, `ready_undistilled`, with no summary label, and fewer than three failed tries (`horizon.DISTILL_MAX_FAILURES`, the kit's own count of failures). A capture whose summary failed three times leaves the automatic queue, so a document the model cannot label is not paid for at every later pass; it says so on its card ("gave up after 3 tries", with the last error), the waiting count leaves it out, and a press that names it (Summarise again) runs it, since a named capture is taken whatever its count. Only the capture's own failures count. A Stop that ends a run, an unreachable model, a provider refusing the key or the account (authentication, permission, an exhausted quota) and a misconfigured server are reported the same way and counted toward nothing (the run wrapper raises the kit's `StepNotCounted`), so a pass run offline or with a bad key caps nothing. A rate limit or a provider's server error is different: it may be the provider, or it may be one capture too large for it, so it counts against the capture, and three in a row stop the pass like an unreachable model does.

## ready_undistilled is a real state

`schema.NodeState` carries it as a first-class value, for invariant 79's reason. A node whose summary failed is still a usable node: it has its origin, blocks and flags, and it can be filed into an orbit and cited. Only a convenience is missing. A failed or cancelled distillation puts the node back to `ready_undistilled` and the pass moves on; it never becomes `failed`, which means the capture itself did not work, and nothing is removed.

That survives the process dying. `horizon._OWNED_STATES` maps each in-progress state to its fallback, and `horizon.reset_interrupted_states` applies it at startup: a `parsing` node has no blocks yet and returns to `queued`, while a `distilling` node has its blocks and returns to `ready_undistilled`. One map, because two resetters is how the second one goes missing; `distilling` was once reset nowhere, stranding nodes in a state nothing selects after a crash. The state then follows the labels: a capture with a summary label is `ready`, since a crash between the kit's label write and the state write would otherwise leave a summarised capture waiting for good.

One pass runs at a time (`_DISTIL["running"]`, which the automatic pass shares), and the run wrapper takes a capture only while it is still `ready_undistilled` and still there: one removed or summarised meanwhile is passed over without a call and without a report.

## What the summariser reads

The kit's steps read the capture's stored text, one item's text with no `[[SRC:...]]` markers, so neither invariant 61's prefix problem (the excerpt exists for a multi-source blob) nor a marker in the result (invariant 62) can arise; the kit strips any marker a model writes anyway. A capture with no text is labelled empty without a call: its item's text is its origin, kept so it is findable, and must not be summarised.

## The language ladder is shorter here

A summary is model-written prose, so invariant 39 applies, but `distil_pending` runs on a background thread with no request, so the interface-language signal (invariant 69) and `Accept-Language` are out of reach. The ladder is `output_language()` (the operator's stated preference), then a language the caller passes, then nothing, in which case the prompt tells the model to follow the document. The automatic pass and organising pass `config.reader_language()`: the interface language the last request carried (`X-Penumbra-Interface-Language`), recorded by the auth middleware in `.reader-language` beside the settings file. Without it, a reader with a Chinese interface and no output language set got English summaries and English orbit names, because most documents were English. It only fills an unset output language, so invariant 48's two settings stay separate; it is kept out of the settings file because it is observed, not chosen, and the settings page draws every key that file holds.

## A short capture is not an RLMTask, and runs in this process

The full REPL loop suits exploring a large corpus with verifiable citations and is absurd for three sentences (the same argument as `naming.py`). Invariant 21 covers `RLMTask` execution, not every model call, so the short step is one `dspy.Predict` call on the pass's own thread; spawning a subprocess per capture would cost more than the call it isolates, and the pass already survives any single capture failing. The long step is an RLM run and goes through the worker.

`import dspy` happens only when a short capture is summarised, so `cli.py`'s imports never pay for it; a subprocess import blocker pins it. The pass uses `asyncio.run`, so it is called from a thread of its own, never from a request handler's loop.

The kit cleans what comes back (markers stripped, lengths capped, tags NFKC-casefolded and deduplicated) and keeps an entity only when the capture's text names it, or, for a long capture, a verbatim quote of it, or when it is a name already in use; Penumbra adds no second cleaning.
