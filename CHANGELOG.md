# Changelog

All notable changes to Penumbra are documented in this file. The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/), and the project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Penumbra is a personal knowledge hub built on [`rlm-harness`](https://github.com/qazbnm456/rlm-harness). It runs as a desktop app that lives in the notch: you throw anything into the Horizon, see how it connects on a star map and in knowledge graphs, ask questions grounded in it with citations you can check, and take a distilled artifact away.

Each entry states what the product does now and why. The reasoning behind each rule lives in [`docs/invariants/`](docs/invariants/), and the rulebook index is [`AGENTS.md`](AGENTS.md). Nothing has been released yet, so everything below is in `[Unreleased]`.

## [Unreleased]

### What it does

#### Capture: the Horizon (Tier 0)

- The Horizon is the default screen. You paste a link or text, drop files, or upload them, and each capture lands at once as a node you can find again later. An orbit is a place you go into, and a node is filed into one or more orbits by copying it (invariant 78).
- Capturing is a drawer at the top edge, the mirror of the ask dock at the bottom: at rest a breathing grip under the header, sliding down when the pointer reaches the grip bar itself (within a few pixels), when N is pressed, or while the field holds text, focus, an error or a dragged file. The trigger is that narrow so reaching for the tag row, the view switch or the legend does not open it. It looks the same on the map and the list, and a drop lands anywhere on the page. The field is not focused on arrival, since that would hold the drawer open.
- The Horizon is an index, not a corpus. Nodes live in a SQLite index plus one JSON file each, every write is a SQL delta, and nothing at Tier 0 assembles a blob, so the Horizon can hold thousands of items without touching the orbit size cap (invariants 8 and 78).
- A capture always lands. Submitting creates a `queued` node before anything is fetched, intake runs one item at a time, and a failed parse becomes a `failed` node that keeps its reason, so a bad link can never stall the queue behind it (invariant 79).
- Everything crosses the Horizon, including what is added from inside an orbit. A pasted link or text, an upload or a promoted note becomes a node filed into that orbit, pointing at the source the orbit already holds, so a summary can read it, it names entities and it can be filed elsewhere; the orbit itself is not changed. Orbits written outside the server, such as by the CLI, are recorded once when the server starts. Taking a source out of an orbit leaves its node in the Horizon, like any capture.
- A capture already in the Horizon is recognised beyond an identical address or text: an address that differs only by what tracks (`utm_` parameters, click ids, a share link's `?s=`, `twitter.com` against `x.com`) is the capture already there, from any capture path.
- A link with Chinese or other non-ASCII characters in it, such as a Chinese Wikipedia page, is fetched percent-encoded, and the capture keeps the address as it was pasted.
- A capture is named the way the list names it everywhere it appears (the waiting card, suggestions, notices): a paste by its opening words, a link without a title by its site, and a Wikipedia page without the encyclopedia's name its title carries. HTML entities in a page's title or description (`&#039;`, `&amp;`) are decoded, including in titles already stored.
- Distillation writes a short title, summary, tags and entities for each capture so it can be found again. It is off by default, because summarising every capture of a 200-bookmark import would silently spend 200 model calls. One pass, automatic or pressed, takes a batch of 20 by default, set by `PN_DISTIL_BATCH` or on the settings page up to 500; the automatic pass leaves long captures for a press unless "Also summarise long captures automatically" (`PN_AUTO_DISTIL_LONG`) is on, which suits a fast or local model. A failed summary leaves the node usable (invariant 80).
- A capture's title and tags are the reader's to change, like a bookmark's name, while its text stays what was captured. The details column and the map's card show a rename button beside the title, a remove button on each tag and a field to add one. A typed tag is cleaned the way the model's are, so `Rust` joins `rust`. Adding past eight tags is refused rather than cut; removing is always allowed. The summary pass never overwrites a title or tags the reader set, even ones set before the summary landed, and the trail dates a summary by when it landed, not by the last edit.
- The Horizon's database records its schema version (`PRAGMA user_version`) and brings an older database up to date in place, one numbered step at a time, so a new column never needs a fresh database.
- How a capture gets into an orbit is a setting, "How new captures are filed", with three choices. Manual, the default, leaves it in the Horizon, where the map's waiting card offers its suggestion. Automatic is for a reader who wants to throw things in and do nothing else: a capture with a clear filing suggestion (shared entities and tags after its summary, or local relations before it) is filed at once with no model call, and at the end of each summary pass one model call places the summarised captures still in no orbit, into an orbit that fits or into a new orbit it names when none does (`organize.py`). One call opens at most ten new orbits, and only for a subject two or more captures share; it leaves a capture rather than put unrelated subjects together. Filing into an existing orbit needs the model to say the capture is about that orbit's subject or a part of it; one that shares only a word, a place or a broad theme is not filed, because “the closest orbit” put a lighthouse into astronomy and origami into Taiwanese history. A capture on a subject of its own that no orbit holds waits in the Horizon and goes to the model again beside the next captures, so its orbit opens when a second capture on its subject arrives. When a call opens orbits and leaves captures, up to two more calls look at what is left, since the new orbits may fit it. A capture the model sent somewhere filing then refused (an orbit the reader declined, or one at the corpus cap) counts as left too, so it is not paid for again at every pass, and on the automatic pass organising gives way as soon as a new capture arrives. The waiting card marks a capture left this way "waiting for a second" and says why, because under automatic filing a capture that stays put would otherwise look forgotten; which captures were left, and against which orbits, is kept in the Horizon's database (`organize_left`), so the note survives a restart. Assign files every capture into one chosen orbit. A capture the reader takes out of an orbit is never filed straight back into it, filing stops before an orbit would pass the corpus cap, and the capture stays in the Horizon either way.
- When automatic filing files something while the workspace is open, a notice names the capture and the orbit, with Take out to send it back to the Horizon, which also stops it being filed into that orbit again; several at once share one notice with the count and how many new orbits were opened. It appears once a summary pass ends, or within half a minute of a capture, when its embedding lands.
- Taking a capture out of an orbit, from its orbit picker, sends it back to the Horizon if it is in no other, warns first when saved citations there point at it, and offers an Undo; it also stops the capture being suggested for or filed into that orbit again. A capture's card on the map can also remove it: filed nowhere, after one confirm; filed into orbits, the reader chooses between the Horizon only, where the orbits keep their copy as the list's Remove does, and every orbit as well, where each loses the source as removing it there would (`DELETE /horizon/{id}?everywhere=true`).
- The list uses the width: like the star map it has the details column, and choosing a capture opens it there (whole summary, every tag, entities, trail, actions) while the list keeps its place and widens. The "+3" after a row's tags is a button that opens the same column. With nothing chosen the column closes and the list takes the width.
- The list is a history: each capture's time to the minute in its own column beside a timeline rail, dates headed by both the relative day and the calendar date, and a card with the title, two lines of summary, its source and size, and the orbits it is in and up to three tags as chips (`GET /horizon` returns each node's memberships). Open, the card shows what it talks about and its trail (captured, summarised, filed into each orbit, each with its date and time), and the full text opens in the reading window rather than being poured into the list.
- While intake or a summary pass runs, the list replaces only the rows whose capture changed, and never a row whose orbit picker is open: that row keeps what it showed and catches up once the picker closes, and a new capture waits the same way rather than repainting the list under the picker. After a capture's tags are edited, a filtered list is asked again, so a capture that no longer matches leaves at once. In the filter panel, picking a tag after typing in its search field leaves the field focused.
- Search reads titles, summaries, tags, entities and origins. Several words must all match, and a query with no spaces (such as Chinese) is matched as one substring. Beside it, Filter combines conditions, all of which must hold: when it was kept (today, the last 7 or 30 days, or between two dates), tags (any or all of the chosen ones, from every tag with its count and a search field), orbits (any, including in no orbit), state (summarised, not yet, could not be read) and what to show (captures as they were added, removals, or both). The conditions in force sit under the field as chips that each come off with a press, and an order button offers newest, oldest, by title or longest first (`GET /horizon`, `GET /horizon/tags`).
- A removal is part of the history, not a row that disappears. Removing a capture records its name, source, tags and the orbits it was in (`horizon_events`), and the list shows it where it happened, struck through and marked Removed, with whether the orbits kept their copy; the same conditions filter removals, except state, which a removed capture no longer has. The record is written in the same transaction as the delete and only when a row was deleted, so a failed or repeated removal leaves no false record. The newest 5,000 records are kept, the oldest going as new ones arrive. Removals have a moment rather than a title or a length, so they are listed only newest or oldest first; in the other orders the choice is shown switched off with the reason.

#### The browser extension

- A browser extension for Chrome, Arc, Brave and Edge (`penumbra/extension/`) keeps what the browser shows.
- It keeps the whole rendered page, so a page behind a login or drawn by JavaScript is kept as the reader saw it.
- The icon says what became of this tab's page: a turning arc in its corner while the page is on its way, a tick once kept, a cross if it failed. Pressing it again acts on that: while the page is on its way it cancels (the capture is taken back the moment it lands), once kept it takes it back and the card offers Keep it again, after a failure it tries again. A page kept before, or more than ten minutes ago, cannot be taken back from the browser, and the card says to remove it in Penumbra. The state lives per tab in the browser's session storage and ends when the tab navigates; a capture that lands after the tab has moved on marks nothing (pages are compared without a text directive but with any other fragment, so a hash route is a page of its own), and one cut off by the browser stopping the extension shows as failed, ready to retry. Reloading the page, or a frame in it, clears the tick while the capture stays kept, so a press after that says it was kept earlier rather than taking it back. Keep it again after taking back a passage or a link keeps that passage or link, not the whole page. Several tabs can be kept at once, and switching away does not stop a capture.
- It keeps a selected passage with the page it came from, whose address carries a text fragment that scrolls back to the passage.
- It keeps a link, which the server fetches like any pasted URL.
- Each capture goes into the Horizon or, from the right-click menu, straight into an orbit. The toolbar button and Alt+Shift+P keep the page. Penumbra's own pages are not captured.
- It answers on the page with a card, as Pocket and Readwise do: what was kept, its title, a menu to put it into an orbit and an Undo, gone after a few seconds unless the pointer is on it.
- A failure says why on the same card, and a second press on a page that is still on its way says so instead of sending it twice.
- With automatic filing, the card says the capture goes into the orbit that fits after its summary, or a new one, or, once the reader has chosen an orbit, that automatic filing will not move it.
- An orbit the reader chooses on the card or in the menu gets the capture even when automatic filing already put it elsewhere. When it cannot (the orbit holds as much text as one question can read, 8,000,000 characters by default, or is gone), the card gives that reason.
- A page captured again after it changed a little (a new count or relative time), or a page with the same title and nearly the same text, is found by comparing character 5-grams with numbers left out (`dedupe.py`), and the card says it is already kept, with Keep another copy. Two different articles on one subject stay two sources.
- When Penumbra is not running the icon is greyed and the menu says so, and a capture is kept in the browser and sent when Penumbra is back (at most 50).
- It pairs from Settings > Browser extension, which shows the folder to load unpacked and opens a pairing page in the reader's browser.
- It holds a capture key that opens only its capture routes, where filing and Undo reach only what it captured in the last ten minutes (invariant 77).

#### Asking the Horizon

- You can ask a question over everything you kept, one tag or one entity, or a tag or entity within one orbit, not only inside an orbit. The first press decides locally, at no cost, which captures the question will read and says how many; the second press asks (invariant 47).
- The captures are picked with a full-text index inside the Horizon's own database. Chinese, Japanese and Korean text is indexed as overlapping character pairs instead of through a dictionary: jieba's default dictionary splits 關係 on Traditional text, every dictionary variant splits 海馬迴 so a search for it finds nothing, and FTS5's own trigram tokenizer cannot match a two-character word at all. The index is derived from the captures and rebuilt on demand (invariant 78).
- A scope that fits is read whole. A larger one reads what the question's words found, best first, up to `PN_HORIZON_ASK_CHARS` (1,000,000 characters, never above the orbit cap) and `PN_HORIZON_ASK_ITEMS` (40). When the words find nothing, it reads the newest captures and says so. Both bounds are set in the environment only (invariant 41).
- Each answer is kept in the Horizon's ask history with the captures it read. Reopening one checks its citations again against the captures as they are, so a removed capture leaves its citations unverified. A question about one orbit is asked inside that orbit and joins its conversation. An orbit chip in the history is marked with a small ring and planet, so it is not mistaken for the theme toggle's `◐`.
- Horizon asks run under the reserved handle `horizon-ask`, so the live ticker, Stop, the Trajectory drawer and recovery after a reload work exactly as they do in an orbit. No orbit id may start with that handle.

#### The star map and the knowledge graph

- The Horizon opens as a star map: the Horizon is the black hole at the centre with the captures filed nowhere circling it, each orbit is a planet whose moons are its captures (copper once summarised, grey before), and a link joins two orbits whose captures name the same entity. A header toggle switches to the list, and the choice is remembered in the browser.
- The map moves: planets travel their rings, moons circle their planet and the accretion disk turns, and all of it holds still while the pointer or focus is on the map, or when the system asks for reduced motion. Picking a planet, opening a card or pressing a tag redraws the map without restarting its motion: each moon, surface and disk carries on from where it was in its loop. While work runs, the map refreshes only when something it draws has changed.
- A planet has one moon per source, so the moons agree with its source count; a source the server has not yet recorded in the Horizon (a CLI addition) is a hollow moon until it next starts.
- A planet is placed once and then stays where the reader puts it. A new orbit takes the next free place outward, in the order orbits began (their first capture), with each ring offering three more places than the one inside it. Dragging a planet moves it along the nearest ring, lighting that ring, and it orbits on from where it is dropped, also onto a ring beyond the outermost. Filing a capture, a chat turn or a new orbit never moves a planet already there, so two planets never trade places. Places are kept on the server (`GET /horizon/map`, `PUT /horizon/map/planets/{orbit}`) and exported in `data/map.json`, the whole-map view zooms out to the outermost ring in use, and a planet's card names its ring.
- The map has settings of its own, behind the gear under Rest in the corner: the inner ring's size and the space between rings (drawn as they change), how many planets the inner ring holds and how many more each ring outward holds, and how often meteors, meteor showers, comets and passing rocks come (off, rare, usual or often). Fewer places on a ring set its planets further apart, and changing either count rearranges every planet in the order its orbit began, including dragged ones, as the panel says beside them. The settings are kept on the server (`PUT /horizon/map/settings`, refused rather than clamped out of bounds) and exported with the places in `data/map.json`; clearing everything keeps them.
- A planet's card has two tabs, Info and Studio. In the studio the reader picks the planet's kind of world (any of the nineteen the map draws, or the one its name gives it), its size from half to twice, how fast it orbits and turns (still, slow, usual or fast), and whether it has rings, and each choice is drawn at once. The style is kept on the server with the planet's place (`PUT /horizon/map/planets/{orbit}/style`), survives a planets-per-ring rearrangement, and travels in `data/map.json`; while the studio is open the map's redraws leave the card alone, so a slider is never rebuilt under the pointer.
- The arrow keys walk the map. Left and Right step from planet to planet clockwise as they stand on screen, from the top, wrapping at the ends; Down goes into the chosen planet's moons, Left and Right step from moon to moon, and Up goes back to the planet. Each step opens its card and moves the camera and focus there, a held key steps at a walking pace, the keys are listed under Keys in What the marks mean, and they are left alone while a field, a menu, the tag picker, a panel grip or a dialog has them. A screen reader hears only where a step went (a planet and its ring, or a moon and its place among the planet's moons) while the card stays quiet, until the pointer is back on the map. The zoom keys (+, - and 0) work anywhere on the map's screen, and Escape closes the map's settings from anywhere.
- The map is something to handle: scrolling or pinching zooms, dragging empty space pans, and +, - and a return button (or the keys + - 0 and Escape) bring it back. Dragging on the map never selects its labels.
- Clicking a planet glides the camera to it and holds it still beside its card. Selecting a planet opens a card with its sources, its most-named entities, a way in, and a button that summarises only that orbit's unsummarised captures, which names the number of model calls before the press and shows progress with a Stop while it runs (invariants 47 and 80). The card heads what it talks about, what was filed from the Horizon and what was added inside the orbit, and says what a hollow moon is.
- Pointing at a moon or at a dot around the Horizon names that capture and its state; clicking opens it in the card with its summary, what it names, where it is filed, its orbit picker and Read it. A selected moon is marked itself, a larger cream-ringed dot with a ping spreading from it, and its planet only by a faint dashed ring, so a selected moon and a selected planet never look alike.
- A question-mark button left of Settings opens “What the marks mean”: every mark the workspace draws, grouped by where it appears (the star map, a capture's state, an orbit's knowledge graph, the list, answers and citations, and the keyboard), one sentence each. The head, with a button per group, stays put while the groups scroll under it, and each sample is the real element drawn by the product's own styles, so the key cannot drift from the screen.
- Clicking the Horizon lists what is filed nowhere, each with its orbit picker, which is also the keyboard's way to do what dragging does.
- Where a capture is filed is one control wherever it appears (the capture card, the list's details, the waiting card): a box that says where it is (in no orbit yet, in one orbit by name, or in several by count), opening a list of every orbit by name with a tick and a highlight on those it is in. Pressing an orbit files the capture there or takes it out, and the list stays open so several can be chosen; a search field appears past six orbits, New orbit… sits at the foot, and the list opens upwards when there is no room below. An orbit it has not loaded yet is looked up, so one just opened and one deleted since are each named for what they are. It replaces a native select, which could do only one thing at a time and could not show a capture in several orbits.
- Dragging a dot from around the Horizon onto a planet files it there, and dragging a moon from one planet to another moves it (`POST /horizon/{id}/move`: filed into the new orbit, taken out of the old; when saved citations there point at it, the reader is told how many and asked first, because they go unverified).
- The carry is drawn like a pin pulled off a map: the dot lifts with a shadow, trails the pointer and stretches as it moves, leans toward a planet it can land on, falls in with a ripple, or springs back when dropped elsewhere. Filing lights the planets it can go to (never one it is already in) and shows an Undo in the notice whenever the filing added a source; the promote response says whether it did, so Undo can never remove a source that was already there.
- Links between planets are details on demand, so they do not tangle as orbits grow. At rest each planet shows only its strongest link, as a faint solid hairline with no label, so there are never more lines than planets; from 15 planets up none is drawn at rest and a small mark says a planet has links. Pointing at or focusing a planet brings out all of its links, thicker for more shared entities and labelled, while the rest dims, and the pointer can move onto one to open it; selecting it keeps them lit, and its card lists what it shares with each other orbit, which stays readable however many there are. The server keeps at least each orbit's three strongest links rather than twelve overall, so no orbit's links are silently dropped. Pointing at a lit link lights it and its two planets and names everything they share, and clicking it opens both sides in the details panel, each side's captures that name the chosen entity, with one press to ask how both orbits talk about it (`GET /horizon/bridge`; a Horizon ask scope takes several orbits).
- On the star map, what waits for the reader is one card in the details column, "Waiting for you", with a section and a count for each kind: captures not yet in an orbit, each with its orbit picker under the title, filing suggestions with their Add and Not this buttons, and captures still to summarise, listed by name above the same Summarise button the list shows. Each section names up to eight and says how many more there are. With nothing waiting it reads "Nothing waiting".
- The map's details column closes only when nothing waits and nothing is chosen, so the map takes the width. When something waits it opens on first paint and each time the count rises, even if the reader closed it last time; closed again while the same things wait, it stays closed until something new arrives.
- The tag row above the star map and the knowledge graph is one line however many tags there are: the chosen tags first, then the most used as far as the width allows, and a button naming how many there are that opens all of them with a search field, where several can be picked in a row. So the row never grows with the Horizon, and every tag stays within reach. Every press acts the first time: a refresh that changes nothing leaves the row and an open picker alone, one that changes only counts writes them into the buttons already there, and a pick updates the open picker in place, so focus in the picker stays where the reader put it.
- Tags on the star map and the knowledge graph combine: several can be on at once, and they light what carries any of them. On the map a lens lights every planet that holds a tag, matched against the orbit's full tag set rather than the six most common it shows, marks the very moons that carry it while every other moon fades, and draws only the links between planets it lit. The card then answers why: every capture carrying one of the tags, with its summary, which of the tags it carries and the orbits it is in, and one press asks over all of them (`GET /horizon/lens`, and a tag scope of several values).
- Studying or asking about an orbit from the star map always opens it, including the orbit just left through the home button.
- Every planet is a world of its own: ocean and continents under cloud, reef islands, dune seas, cracked lava, ice, a banded giant with a storm, cratered rock, jungle or toxic haze, drawn from a seed of its orbit's name so it is the same world every visit, turning slowly, with no two alike on a map while kinds go round. Moons are small irregular rocks, each its own shape, and keep their colour for what it means.
- The rings sit far enough apart that a planet with its moons and label clears one on the next ring, and the map grows outwards as orbits are added. The default view fits the outermost ring that holds a planet, not the empty rings drawn beyond it. When two planets on different rings actually touch (one's body and moons, or its name, meeting the other's), the one behind (higher on the screen) fades until they part, and the planet picked or pointed at always stays clear. Nothing is reordered and nothing is blurred: moving planets within the drawing, or blurring one inside the map's SVG, makes WebKit redo the whole map on the main thread, which shows as a hitch in the orbit. The code that runs every frame reuses what it can, so garbage collection does not pause the orbit either.
- More kinds of world follow the classes exoplanet surveys name: a ringed giant whose rings pass behind and in front of it (gas and ice giants are often ringed too, and a few barren or icy worlds), a blue ice giant, a glowing hot Jupiter, an ocean world, a tidally locked eyeball world facing the light, a carbon world glinting with diamond, a sulfur world of volcanic vents, a cloud-wrapped world and a red dusty one, and a double planet, two worlds turning round each other inside the planet's circle, with a gap between them and the moons outside.
- The sky has weather: meteors, now and then a shower, a comet crossing slowly, a rock tumbling past. They move in the map's own frame loop rather than as CSS animations, because starting a keyframe animation on an SVG element makes WebKit restyle the whole map. Behind the planets sit soft nebulae, far galaxies and double stars, drawn with gradients so the camera can move over them freely.
- The star map rests. Left alone on it for a while (5 minutes by default, set in Settings, or at once with the moon button by the camera; only while its window is the one in use, so time spent in another app never makes Penumbra go full screen and come to the front), the interface steps aside, the map fills the window, every label on the map goes, the camera drifts slowly and the weather comes more often. It never starts by itself while something is running, and with reduced motion it is a still sky.
- At rest the time sits bottom left with, opposite it, something the reader kept: a summarised capture picked at random, its title for a glance and its whole summary and the entities it names (as copper chips that wrap rather than overflow) for a stay, in a reading column paged at sentence boundaries when long, each page held for as long as it takes to read (read from the index, no model call). A key, a click or a nudge of the pointer brings the interface back at once.
- In the desktop app rest fills the screen by itself (macOS simple full screen, no new Space), hides the pointer and the island, and ends within a fifth of a second of a key or a nudge (the borderless window gets no pointer events, so the shell watches the pointer and tells the page), giving the window its frame back on the way out; a browser can do that only when Rest is pressed.
- An orbit opens as its knowledge graph, a map of what connects in which each mark means one thing. A dot is a capture. A pill is an entity two or more captures name, with how many, joined by a line to each; an entity one capture names adds no connection and is listed when that capture is pointed at. A dashed line joins captures whose text is alike. A tinted region is a tag two or more captures here share: each capture sits in the region of its most shared tag, a capture whose tags are its own is in none, and the region is captioned and counted as the tag row counts it, in its own hue. Its name is a handle: pressing it presses the tag, lighting those captures, listing them in the panel and scoping an ask to them, and the side panel says when a region appears. Labels sit on a halo so lines never cut them and are pushed apart until none sits on another; regions never overlap. Only shared entities are drawn because joining every pair of entities a capture names turns it into a mesh of triangles, and a region is only ever a tag so that its name and count always agree with the tag row. Tags are lenses above the graph that light up what carries them. The side panel lists the captures behind a selection, and the header toggle switches to the three columns. An orbit with no sources yet opens in the columns, where they are added.
- Pressing a capture on the knowledge graph opens it in the side panel: its summary, the entities it names (each a press away from that entity), the captures here that name the same things or read alike, most in common first, and Read it for the full text. The capture, what it names and those captures light while the rest dims. Every capture listed in the panel opens the same way, so the graph can be walked from one capture to the next.
- The knowledge graph is handled like the star map: scroll or pinch zooms around the pointer, dragging empty space pans, and zoom in, zoom out and return sit in the corner (+ - 0 from the keyboard). A capture or a hub can be dragged; the nodes one link away follow at 60% and two links away at 30%, easing after it so the cluster keeps its shape, and a node dropped on another pushes it clear. Return puts the camera and every node back. A click on empty space lets go of the entity or tags picked. Its details panel resizes and puts away like the map's.
- Relations come only from what a summary wrote, never from a model call made to draw the picture. An unsummarised capture names nothing, so it is counted in its own box with the spend button rather than drawn as if it were linked (`topology.py`, invariant 78).
- A summary counts named concepts as entities (a theory, a method, a stage, a part of the body) as well as people, places and products, and keeps tags for broad subjects. That is what gives the graph nodes worth drawing.

#### Summaries, concepts and filing

- A short capture is summarised by one call that reads all of it, up to 12,000 characters. A longer one is summarised by an RLM run in a worker subprocess that reads the whole document from a map of its sections, the way a planner is handed a compact summary of a tree; each entity it names carries the coordinate of a block that names it, checked before SUBMIT and again by the host, which drops any it cannot find (invariants 21, 67 and 80).
- Every summary is shown the tags and entities other captures already use, the 80 and 60 most used, and writes the same label when it means the same thing; a new tag is written in the output language. Summarised one at a time with no view of the rest, captures on one subject wrote `coffee` and `咖啡` or `finance` and `金融`, and the tag regions and shared entities missed them. Only the labels are shown, never other captures' summaries, so the prompt stays a few hundred words however large the Horizon grows. Labels written before this stay as they are.
- The summarise buttons state the cost before the press, as a range when long captures are waiting (`/horizon/distil/estimate`), and Stop ends a long-document run at once rather than after it finishes.
- When summaries fail, one card on the Horizon groups them by cause (the model could not be reached, it ran out of time, its reply could not be read), each with how many it hit in words ("1 affected"), one line on what to do and the captures it hit, three named and the rest behind a disclosure, and retries exactly those with one press. On the star map it is a section of the waiting card rather than a bar under the map. The reason is also recorded on the capture, so after a restart the card still says why it failed; a summary that succeeds clears it, and dismissing the card forgets it. When the model cannot be reached three times in a row the pass stops, since every later capture would fail the same way, and the rest stay waiting; a failure to reach the model is never retried as if the reply were at fault. A long document is given time in proportion to its length, one `PN_RUN_TIMEOUT_SECONDS` per 15,000 characters, up to five, so a large PDF gets the time a short page does not need.
- Concept alignment runs once at the end of a summary pass the reader pressed (never after the automatic one, which runs on the intake thread), over the entity names no alignment has seen, and decides which are the same thing (Matthew Walker and 馬修·沃克). The answer is an alias table every reader applies: the star map, the graph, the tag and entity lists and scoped asks. Stored summaries are never rewritten, so a merge is undone with one press in the graph's side panel, and an undone pair is not proposed again (invariant 80).
- Filing suggestions are computed locally: a capture in no orbit, or only in the assigned orbit, is offered for the orbit whose captures share at least two of its entities, or one entity and one tag. Nothing is filed until the reader presses Add, and a declined pair is not offered again.

#### Local relations

- Settings has a Local relations row: one press downloads an embedding model (multilingual-e5-small, int8, about 130 MB) pinned to one revision and checked against its SHA-256, with progress and a Stop; another deletes it and every stored vector. Nothing is bundled, so a reader who never turns it on pays nothing (invariant 82).
- With it on, every capture is embedded on this computer in the background, free and without a model call, and the knowledge graph draws a dashed line between captures whose text is alike, including an unsummarised capture, which is otherwise not linked to anything until it is paid for. Filing suggestions can offer an unsummarised capture for the orbit of the filed capture it most resembles.
- The signal is kept weak on purpose, because similarity on this model sits in a narrow band and leans towards text in the same language: a line needs a score of 0.86 and mutual nearness, text under 40 characters is not compared, and a similarity suggestion ranks below one by shared entities.

#### Asking from anywhere

- The ask panel rests as a handle at the foot of the star map, the list and the knowledge graph, and slides up when the pointer reaches the grip bar itself, within a few pixels, so reaching for the legend does not open it. At rest it is only a grip that breathes, and while it is open the map's legend and summary note fade out beneath it.
- Its scope follows the selection on screen: everything, a tag lens, a planet, or an entity or tag inside the orbit on screen. An orbit chip asks straight into that orbit's conversation in the three columns; every other scope is a Horizon ask.
- Any other scope is chosen from a staged picker, opened by the + beside the chips or by typing / at the start of the question: tags, entities and orbits with their counts first, then the names in the one chosen, with the arrow keys, Enter and Escape; typing searches every kind at once. It is staged rather than a native select, which lists every name in one column that runs off the screen.
- Every place a question is written uses the orbit composer's box: the text on top, a row of keycaps under it saying what Enter does in this view and whether it costs anything (one word each: preview, or ask in an orbit, then new line and commands, since `/` is where commands will live; the picker's own keys while it is open), and one round send button that fills once there is text; only the controls a view needs, such as the scope chips, sit above it.

#### Orbits and grounded chat

- Ingestion covers text, web pages, PDFs (including scans, through local hybrid OCR that ships on by default), Word documents and YouTube captions. Ingestion runs on the host and one source at a time, because PDFium is not thread-safe and concurrent PDFs crash the process (invariants 3, 7 and 33). A PDF that fails to parse is reported by the uploaded file's name, not the server's temporary path.
- OCR uses `rapidocr`, which runs on Python 3.13 and 3.14, and PDFs are read with `pypdfium2` rather than `pymupdf`, whose only licences are AGPL or commercial. OCR reads two-column scans in reading order, and a garbled PDF text layer is detected by comparing it with OCR rather than by a threshold, since no threshold separates good pages from mis-decoded ones (invariants 73 and 74).
- Word documents (`.docx`) can be captured, uploaded to an orbit or passed to the CLI. Each heading starts a citable section (`section:N`), whether it carries a heading style or is written, as other apps do, as a short bold line of 14pt or more; a long stretch without headings is cut into sections at paragraph boundaries, and tables and lists keep their shape. It is read with the standard library, and the document is size-checked before it is decompressed.
- A YouTube capture is named by the video's title and channel from the moment its captions are read, taken from the same lookup that finds them, with the start of its description as the preview; no thumbnail is shown (invariant 51).
- An orbit is one JSON file. Every write re-reads it inside a per-orbit lock and applies a delta, so concurrent writes cannot silently drop data (invariant 34). Source ids are never reused, so a saved citation can never start pointing at different text after a source is removed (invariants 12 and 50).
- Questions are answered by an RLM run in an isolated subprocess and a Pyodide sandbox, with the previous turns as context only, never as a source of facts (invariants 9, 11 and 21).
- Answers come back in the reader's language while citation coordinates stay exactly as the source has them. The interface language is a separate browser preference, and it counts as a signal when the orbit's output language is first chosen (invariants 39, 48 and 69). With no output language set, work that runs with no request (the automatic summary pass and organising captures into orbits) follows the interface language the reader last used, and the settings page's empty choice says so: "Follow the interface language".
- Model-written prose is tidied on the way to the reader by fixed rules, with no model call: announcing openings ("本文件為", "This document describes") and empty signposts ("總的來說", "In summary,") go, dashes become commas (a number range keeps a hyphen), and ASCII punctuation between Chinese characters turns full-width. It applies to answers, overviews, guides, podcast transcripts, Horizon asks and capture summaries; stored text is untouched, and citation highlights are tidied the same way so they still land (invariant 62). The summary prompts name the Chinese openings as well as the English ones, because the English rule alone does not stop them.
- Each answer carries follow-up questions from the same run, at no extra cost (invariant 56). A chat answer can be regenerated, and a conversation can be cleared.
- Notes are free text that can be promoted into a real, citable source. A note on its own is never cited (invariant 32). An answer can be kept as a moon in one press: it becomes a source of the orbit, a moon on the map, and later questions can cite it. A note's promote button says the same, Keep as a moon.
- An orbit names itself from its sources, can be renamed at any time, and can be deleted (invariants 37 and 53). An orbit with no title yet is named after its first source's own title (a page title, or a file name without its extension), not a URL segment and a count.
- Deleting an orbit is refused while any work on it is in flight, including audio synthesis. An orbit that disappears mid-synthesis takes its audio with it, so a later orbit of the same name is never served someone else's episode.
- An orbit's columns are the study view, named so ("Study", 研讀): where one orbit is read in full with the AI, with citations, a conversation and the Studio's guides, as opposed to the star map, which is for scanning. A planet's card opens it with Study it, and a lens card whose captures all live in one orbit offers the same.

#### Model runs

- Every RLM task carries `rlm_harness.skills`. Anything that would corrupt the output if skipped stays in the prompt (invariant 65).
- Budgets are sized against measured distributions: `max_tokens` is 32768 because a smaller cap cuts replies off mid-JSON, and the run timeout is 300s for API models and 1800s on the subscription path, scaled up for long podcasts (invariants 59 and 68). A guide or an answer has 25 REPL turns, a long-document summary 15 and a concept alignment 8, or the configured budget when that is lower, so a small decision cannot spend an orbit-wide guide's turns.
- `PN_MAIN_LM_KWARGS` and `PN_SUB_LM_KWARGS` pass extra model settings to one role, chiefly a thinking budget for a reasoning model, and `PN_REQUEST_TIMEOUT` bounds one model request (invariant 59).
- No run reads the model response cache. dspy caches every call on disk by default, so a summary pass, a concept alignment or a first overview tried again after a bad reply would get the same reply back in seconds.
- A summary pass or concept alignment whose model reply could not be read is run once more, fresh, before it counts as failed. A question, a guide or a podcast stays one press, one run.
- Answers, guides and podcast scripts get `source_index`, a table of contents of the corpus built from its markers (each source's size, then its blocks with marker, size and opening words, bounded at 16,000 characters), and are told to read it first and then read the passages themselves. It is derived inside the shared task base from the blob the run is given, so no caller builds its own. A sibling project measured an answer dropping from 8 turns to 3 once it had one.
- The validator's description and its success line say to pass the value to `SUBMIT` from code on the next turn, matching the shared rule that every reply is reasoning plus code; a model told to "output this JSON string" can reply with the JSON itself and fail on the parse.
- Every task is told that a triple backtick anywhere in a cell, strings included, is read as a code fence and can discard the turn, and to build a fence with `chr(96) * 3`. Concept alignment's validation paragraph names only the checks its validator runs, and the skills catalog asks for whichever skill is relevant instead of all of them first.
- The corpus-navigation skill says to read generously and measure coverage, and to slice quotes out of `sources` rather than retype them, since a sibling project measured the opposite advice as the cause of its thinnest results.
- Each run's trace records, at its start, the generation cap and thinking budget each role's model actually carried, so a run killed at its time limit still shows them. The worker's stderr reaches the server log, and a timeout says it may be a runaway rather than only a slow model.

#### Citations you can verify

- Every grounded task echoes opaque `[[SRC:<id>|<locator>]]` coordinates, and a validator checks each citation's coordinate against the corpus before the run may submit (invariants 4, 13, 66 and 67).
- Verification proves that a coordinate exists, not that the quote supports the claim, and nothing in the product says otherwise. A citation that does not resolve, for example after its source was removed, is shown as unverified on every surface and in every export (invariant 5). Removing a source re-verifies every saved citation on screen right away.
- Citations are numbered by the interface, never by the model, and the numbers follow reading order on every surface: answers, the overview, the four guides and the podcast transcript (invariants 48.5 and 49).
- Pointing at a citation lights up its reference and the reverse. Opening a citation marks the cited words in the References card's passage and scrolls them into view. Clicking a source opens its full text in a viewer (invariant 58).

#### Studio

#### Server, CLI and deployment

- `penumbra serve` starts the API and the web UI on loopback. Every request needs the API token the server prints, and a non-loopback `--host` warns, because the token authenticates the app and there is no per-user authorization (invariants 25 and 77).
- `serve` quits on one Ctrl-C or a terminal hangup even with a run in flight, and it kills the run's whole process tree, so no worker keeps billing after the server is gone (invariant 22). Cancellation goes through `runner.kill_tree`, which works on Windows too, where `os.killpg` and SIGHUP do not exist.
- The package and command are `penumbra`, the API lives at `/orbits` and `/horizon`, every setting is `PN_*`, and an orbit id the interface mints or derives starts with `orbit-`. Prompts the model reads call an orbit a "collection", a word it understands without context. Penumbra grew out of rlm-notebook, a NotebookLM-style notebook with a web server; its data and `RN_*` settings are not carried over.
- `rlm-harness` is pinned to 1.13.0, and the worker uses only its public API. `dspy` is held below 3.4, because dspy 3.4.0 made `RLM.aforward` keyword-only while rlm-harness passes the sandbox positionally, so every RLM run fails with "aforward() takes 1 positional argument but 2 were given"; rlm-harness itself asks only for `dspy>=3.3.1`.
- A model string prefixed `claude-agent-sdk/` runs that role on the user's Claude subscription (invariant 35). The desktop app supports it with nothing to install beyond Claude Code itself: it carries the SDK's Python (under a megabyte) and drops the 260 MB copy of Claude Code the SDK's wheel bundles, because a subscription run needs Claude Code installed and logged in anyway, and the SDK then uses that one. Without Claude Code, the error says to install it and log in.
- A `Dockerfile` carries the two binaries no Python manifest can express, `deno` and `tesseract`.
- The CLI can ingest, ask, generate guides and podcasts, and write a trace with `--trace`. It cannot reach the Horizon or manage orbits.
- The agent guide is `AGENTS.md`, an index of the invariants with one argument file each under `docs/invariants/`. `CLAUDE.md` is a one-line bridge.

#### The desktop app

- The start screen plays one of ten short scenes of Penny, the half-lit moon: watching Wu Gang chop the osmanthus, the Jade Rabbit pound the elixir or Chang'e fly to the moon on television, tripping and crying, a bubble tea, a mooncake, a sky lantern, a pomelo-peel hat, a doze and juggling planets. Pointing at it turns it into an ordinary hover, and it never interrupts a drop or a note.
- A thought can be written straight into the island. A pen on its hover shape, or Write a Thought… in its menu, opens it into a one-line field with the ring at its left end and a hint saying Return keeps the line and Esc cancels. Return sends the line to the Horizon (a lone link is captured as a link) and the line falls into the ring; Escape or clicking anywhere else puts it away and keeps the line for next time.
- Resting the pointer on the island for a few seconds offers to take a thought: a line fades in under the ring saying typing works, and the first key opens the note field with what was typed. Moving away puts it back. The pen lights under the pointer even while Penumbra is in the background, from the pointer position the shell reports.
- A thought typed with Zhuyin, Pinyin or Kana reaches the Horizon: the field keeps its own keys (the island's Return otherwise opens the workspace), tracks composition itself, and ignores Return and Escape while the input method owns them, so Return while composing picks the candidate instead of sending.
- The island takes the keyboard only while it listens or holds a note. When it puts a thought away it hands the keyboard back to the app that had it: it remembers that app and, as macOS's cooperative activation asks, yields to it and brings it forward, since deactivating alone leaves no app active and typing goes nowhere.
- The builds are unsigned: macOS carries an ad-hoc signature on the app and every bundled binary, Windows and Linux none. A manually run CI workflow checks the shell and builds every installer on all three platforms; the Windows and Linux builds have not been run yet.

### Security

- The SSRF guard is re-checked on every redirect hop, and operators behind a fake-IP resolver can carve out a range with `PN_FETCH_ALLOW_CIDRS` (invariants 2 and 76).
- A shortened or redirected link is captured as the page it leads to, shown with what it passed through ("via t.co"). The server follows at most five hops, each checked by the SSRF guard, with no cookies and no script, and the reader's browser never opens it. A wrapper that carries its destination in the address (a Facebook or Google click-through, an Outlook Safe Link) is unwrapped from the address without contacting it. No destination is sent to a reputation service, since that would send every captured address off this machine (invariant 2).
- The chat task has no network tool, `add_sources` accepts only http(s) URLs, and no upload surface can read a server path (invariants 1, 26 and 30).
- Source previews never reference an image, so a pasted link cannot turn the reader's browser into a beacon (invariant 51).
- Model-written Markdown is rendered by a DOM builder with no `innerHTML`, and links in answers are shown but not clickable (invariant 55).
- Injection-scan flags are shown but never block a run (invariant 6).

### Decided against

- A public demo page. A static, server-free replay of the web UI (`playground/`) ran at `boik.tw/rlm-notebook`; it showed a NotebookLM-style product that Penumbra is not, so the page was taken down and the builder removed.
- Concurrent source ingestion, because PDFium crashes under it (invariant 3).
- A Traditional Chinese OCR recognition model and a layout-detection model as shipped defaults, because measured accuracy did not justify them.
- A phone layout. This is a desktop application, and the server binds loopback.
- A graph drawn from sources added straight into an orbit. Only captures filed through the Horizon carry entities, so such an orbit's graph says there is nothing to draw and points to the columns.

### Known limitations

- Export everything builds the zip on the server, then hands it to the page as one download, so a very large Horizon passes through the page's memory in one piece. There is no restore from an export yet, and no CSV, Readwise or Zotero file in it.
- Guides are not persisted, and a guide run that outlives an orbit switch cannot be recovered.
- The in-memory run maps have no multi-worker story, and the API has one shared token with no accounts.
- Traditional and Simplified spellings of the same word do not match each other in Horizon search, and a Horizon ask stands alone, with no follow-up thread. The Horizon's find box matches summaries, tags and origins by substring; the full-text index serves asks.
